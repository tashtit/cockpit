# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, GitHub Copilot) when working with code in this repository. `CLAUDE.md` is a symlink to this file.

## Commands

- `npm run dev` — Electron app with HMR
- `npm run typecheck` — `tsc --noEmit` (there is no linter; this is the static gate)
- `npm test` — all vitest tests (unit + component tiers)
- `npm run test:unit` / `npm run test:component` — one tier
- `npm run test:coverage` — unit + component with a combined v8 coverage report in `coverage/`
- `npm run test:coverage:unit` / `npm run test:coverage:component` — one tier, scoped to the code it exercises (`coverage/unit`, `coverage/component`); these are what CI uploads
- `npm run test:e2e` — Playwright E2E against the built app (run `npm run build` first)
- `npx vitest run tests/indexer.test.ts` — one test file
- `npx vitest run -t "pattern"` — tests matching a name
- `npm run build` — production build into `out/`
- `npm run package` — macOS disk images + zips into `dist/` via electron-builder (unsigned without Apple credentials; version `0.0.0` outside a release)
- `npm run test:packaged` — Playwright smoke test against the `.app` from `npm run package` (`tests/e2e/packaged.spec.ts`; opt-in, uses the real userData dir)
- `npm run docs:dev` — the user guide (VitePress, `docs/`) with hot reload; `docs:build` / `docs:preview` for the built site
- `npm run ui:tour` — builds, then screenshots every view and state against a hermetic fixture world (`scripts/ui-tour/`): desktop and the 560×420 floor, sessions actually flying and landing (stub agent CLIs stream slowly), and a first launch. Writes `test-results/ui-tour/` with an `index.html` contact sheet; a shot it can't reach is marked missing and fails the run. `-- --only chat,settings` narrows it, `-- --no-live` skips the ~40s of live turns

Both `npm run typecheck` and `npm test` must pass before delivering.

## Architecture

Cockpit is an Electron desktop hub that indexes and drives Claude Code / Codex / Copilot CLI sessions (macOS-focused, dark-only). Three processes with a strict boundary:

- **main** (`src/main/`) — all Node work: fs scanning, git, spawning provider CLIs.
- **preload** (`src/preload/index.ts`) — contextBridge exposing `window.cockpit`.
- **renderer** (`src/renderer/src/`) — React 19 UI, fully sandboxed (`contextIsolation`, `sandbox: true`, navigation blocked). No Node access, hand-written CSS (no Tailwind, no component library).

The entire IPC surface is the `CockpitApi` type in `src/shared/contract.ts`. Adding a capability means touching four places, in order:

1. `src/shared/contract.ts` — the `CockpitApi` method and its channel name in the `CH` map
   (`PUSH` for an event); request/response types go in `src/shared/types.ts`
2. `ipcMain.handle(CH.yourChannel, ...)` in `src/main/index.ts`
3. bridge method in `src/preload/index.ts` calling `ipcRenderer.invoke(CH.yourChannel, ...)`
4. renderer call via `src/renderer/src/api.ts`

The two shared files are split so the dependency direction stays one-way: `types.ts` is the
domain vocabulary and imports nothing from `src/`, `library.ts` imports `types.ts`, and
`contract.ts` imports both — `tests/shared-purity.test.ts` fails if that direction is
reversed, since TypeScript compiles a type-only cycle happily. Channel names are never
written as string literals — `tests/ipc-channels.test.ts` fails on a bare literal, on a `CH`
member only one side uses, and on a name that breaks the `domain:verb` shape.

`CockpitApi` is ~100 members under `/* ---------- topic ---------- */` banners, and `CH` is
grouped by channel prefix: put a new method and its channel under the group that owns the
question rather than at the end. The member order is not kept in step across the three files —
don't spend a pass aligning them.

**Renderer input is untrusted.** Any path arriving over IPC must be validated against roots the indexer itself derived — see `assertKnownRepoRoot` in `src/main/index.ts`. Never act on an arbitrary renderer-supplied path.

### Indexing pipeline (the core data flow)

`SessionIndexer` (`src/main/indexer.ts`) walks registered source dirs (`~/.claude`, `~/.codex`, `~/.copilot`, plus extras from config) → per-provider parsers in `src/main/parsers/` produce `SessionMeta` → `repos.ts` resolves each session's cwd to its git repo *and its branch* (worktree-aware: linked worktrees group under the main repo but keep their own HEAD; GitHub `owner/repo` read from the origin remote) → the renderer only ever sees `RepoGroup`s and paged `SessionPage`s. Sessions archived or deleted in the provider's own app are dropped (`provider-archived.ts`), and the history-window setting (`historyDays` in config) hides sessions idle longer than N days.

Performance invariants — all deliberate, keep them:

- The full index is never shipped to or rendered by the UI. Always paginate.
- Meta parsing reads at most 256KB per file. Parsers are failure-tolerant: session log formats are provider-internal and drift between releases, so skip anything unreadable rather than fail the scan.
- A parser reports only what its log states (`SessionMeta.logBranch`), never what the disk says. Anything derived from the checkout — `repo`, `isWorktree`, `gitBranch` — is the indexer's `annotate()`, is recomputed on every scan, and is stripped before the stat-cache is written so a renamed remote or a moved worktree can't freeze into it. Branches are the live example: Copilot stopped writing `context.branch` after CLI 1.0.80 and most Codex rollouts carry no `git` block, so for those the checkout's HEAD is the only source.
- The stat-cache (mtime+size, persisted to userData) means restarts only re-parse changed files; scans yield to the event loop so IPC never blocks.
- Only per-provider session roots are walked/watched (never `pkg/`, `repos/`, logs, or SQLite files). Watching uses Node's `fs.watch(root, {recursive: true})` — chokidar was dropped on purpose (its bundled fsevents broke on the Electron 43 upgrade); the indexer does its own debouncing.

### Other main-process subsystems

- `chat.ts` — spawns provider CLIs headless (`claude -p --output-format stream-json`, `codex exec --json`, `copilot -p`) and parses their stream events. Both old (`msg.type`) and new (`thread.started`/`item.completed`) Codex event shapes must stay handled. A turn can also go over ACP instead (see below); `resolveAcpAgent` decides which, and everything else about the turn — cwd checks, BYOK env, the config home, `busySessions()`, `cancel()` — is the same either way.
- `acp.ts` + `acp-core.ts` + `src/shared/acp.ts` — the Agent Client Protocol: JSON-RPC 2.0 on an agent's stdio. It is an open editor-to-agent standard with broad CLI support, which is what makes "support another agent" a config row rather than another parser. It is the *better* transport for a CLI that offers it — `copilot -p` streams plain text and never announces a session id, while `copilot --acp` gives typed tool calls, a real session id, working resume (`loadSession`) and permission requests Cockpit can actually answer. **Sessions stay indexed**: an ACP agent is always declared against one of the three providers, and `copilot --acp` writes the same `session-state/<id>/events.jsonl` its CLI always did, so the parsers, liveness and attention need no changes at all (`client_name: github/acp` is the only tell). One process per turn, not a pooled connection — that is what keeps `RunningTurn` honest; `session/load` makes the conversation continuous anyway, and its replay is swallowed rather than re-printed. Cockpit claims neither the `fs` nor the `terminal` client capability, and agents fall back to their own tools when a client declines. Built-ins live in `BUILTIN_ACP_AGENTS` (never in config, so an upgraded CLI needs no migration) and apply only once a real `initialize` handshake has answered at startup — a `--acp` flag in `--help` proves the flag parses, not that the protocol works. A user-defined agent is `{command, args, env}`, i.e. "run this binary", which makes `sanitizeAcpAgent` the most security-sensitive validation in the app: bare names or absolute paths only (a relative command would resolve inside the repo being worked on), and `BLOCKED_AGENT_ENV` refuses every name that turns a benign command into a loader for code the definition never mentions. `-core.ts` holds the IO-free half — the `session/update` → `ChatEvent` mapping and the permission decision, where `auto-edit` finally means what it says (file work proceeds, anything that executes still asks) — and is what the unit tests target; `tests/acp.test.ts` drives the real client against a stub agent over a real pipe.
- `roundtable.ts` + `roundtable-core.ts` — multi-agent roundtables: several agent CLIs share one transcript and working directory through the same `ChatManager` (index.ts routes their stream events to the manager, never to the plain-chat channel). A user message opens a parallel wave (every seat streams at once); "one more round" relays sequentially so seats answer each other. Consensus tables (`mode: 'consensus'`) keep running discussion rounds on their own until every seat ends with `CONSENSUS: agree — <one-liner>` (parsed off by `parseStance` into `stance`/`stanceNote`, capped by `maxRounds`), then conclude with **no extra AI turn** — the outcome panel is assembled by the renderer from the seats' own stance lines; a new user message reopens the cycle. `-core.ts` holds the IO-free relay/prompt logic (what the tests target); the manager persists tables to `userData/roundtables/` and pushes `roundtable-event`s. Seats with a session id resume on delta prompts (`seenUpTo` = what the turn was prompted with, so wave replies are never skipped); copilot never announces one, so its seat rides full-context prompts with its own lines labeled "You". The provider sessions seats spawn are not independent work: the indexer (via `tableIdForCwd`) keeps them out of every normal listing, they page only under `SessionQuery.roundtableId`, and `chat:send` refuses their cwd (read-only debug view in the tree).
- `src/shared/endpoints.ts` — custom model providers (BYOK): pure validation, env translation (`COPILOT_PROVIDER_*` for Copilot, `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`/`*_CUSTOM_HEADERS` for Claude; Codex unsupported — it would need config.toml writes), and the provider `/models` listing request/response shapes. Definitions live in cockpit config; API keys never do — `secrets.ts` encrypts them with the OS keychain (Electron safeStorage) into `endpoint-keys.json`, and `endpoint-models.ts` fetches+caches each provider's model catalog. `chat.ts` injects the env per turn, and `index.ts` persists which provider each session started on (`sessionEndpoints`) so resumes stay on that backend and refuse loudly if the provider was removed.
- `liveness.ts` + `liveness-core.ts` — live status for the sessions Cockpit did not spawn (terminals, the providers' own apps: most of them). `ChatManager.busySessions()` only knows its own processes; the rest is derived from the logs, in main, off the indexer's watcher: every fresh parse of a changed file (`metaFor`) hands the file to the `LivenessTracker`, which — for files written inside the freshness window only (mtime, capped by the log's own last timestamp so a restored or synced file is never a phantom) — reads a bounded tail (`LIVE_TAIL_STEPS`: 64KB, then 1MB, then the 4MB transcript cap, each step only when the one before held nothing decisive; a single tool result or screenshot asset can be that big) and `-core.ts` judges what the records say — Claude by the newest message record (a prompt, tool result or tool_use is mid-turn, a text-only answer or the `stop_hook_summary` is the end; content blocks decide, not `stop_reason`, which the desktop harness stamps `end_turn` on tool_use records), Codex by its `task_started` / `task_complete` / `turn_aborted` brackets, Copilot by `assistant.turn_start` / `turn_end` / `session.shutdown` and `user.message` (an open `ask_user` or `exit_plan_mode` call is a question, not a tool, and outranks any tool started after it — the person is still what the turn waits on). Every unrecognised shape is idle, and a tail with nothing decisive in it is silence (`null`): a turn already seen running stays running through it — a turn's end always writes a small decisive record — and one never seen is not invented. A killed CLI leaves a mid-turn tail forever, so entries expire on a sweep after `LIVE_WINDOW_MS` without a write — `LIVE_TOOL_WINDOW_MS` (ten minutes) while the newest record is a tool call without its result (`TurnVerdict.inTool`: a Claude `tool_use` line, a Codex call item, a Copilot `tool.execution_start` with no `tool.execution_complete` for its id), because a test suite writes nothing for minutes; Copilot is the one provider that says so itself, so a Copilot entry past either window is kept while the pid in an `inuse.<pid>.lock` beside its log is alive (`copilotLockPids` names them, `process.kill(pid, 0)` answers — a pid we may not signal is not ours but a recycled one, so it counts as gone; a bounded `opendirSync` read of `LOCK_SCAN_ENTRIES`) — that is how a CLI killed mid-tool is told from one still working, and because Copilot leaves its locks behind on a crash the pid is the evidence, never the file: a lock only ever *keeps* an entry the log already showed running, and a missing, unrecognised or dead one leaves the windows to decide; the arrival gate stays `LIVE_WINDOW_MS`, so a cold scan reads no old tails; Claude subagent transcripts (`<session-id>/subagents/**`, never indexed) count as the parent's heartbeat because the parent log is silent while they run. `index.ts` merges both halves (`mergeBusy`, spawned wins on a shared id) into the one `busy-sessions` push and `sessions:busy` answer, tagged `BusySession.source`. `-core.ts` is what the unit tests target; `tests/liveness.test.ts` drives the tracker over real tmpdir logs.
- `attention.ts` + `attention-core.ts` — telling the user an agent needs them: a desktop notification, a macOS system sound (`afplay` on `/System/Library/Sounds`, nothing third-party shipped) and a Dock badge. Three inputs feed the tracker, all landing under one rule (on screen in a focused window is not news). (1) Turns Cockpit spawned: `ChatManager`'s `onTurnStart`/`onTurnCancel` hooks and its stream events (seat turns are skipped — the table lands once on a `round` event with `running: false` and no `stopped`), so a stopped turn or a closed window is never news. (2) Turns *observed* in the logs of sessions run elsewhere (terminals, the providers' own apps — most sessions): the `LivenessTracker`'s `onTurn` events, emitted only from decisive records — `ended` when a turn seen running writes its ending record (`failed` when Claude's is an `isApiErrorMessage` record; an expiry after `LIVE_WINDOW_MS` is silence, never a landing: a killed CLI or a long tool call must not chime), `asks` when the newest record is a question or permission prompt (`TurnVerdict.asks` from `liveness-core.ts`: Claude `AskUserQuestion`/`ExitPlanMode` tool_use with no result, Copilot `permission.requested` with no `permission.completed` for its `requestId` and its `ask_user`/`exit_plan_mode` tool calls with no `tool.execution_complete` for their id — the same two shapes Claude has, which arrive as ordinary tool calls and would otherwise read as a long-running tool, Codex `request_user_input` with no output and its approval-request events; Claude's ordinary permission prompts leave no record, so they can't be told from a long tool), and `running` when the log moves on — which also clears that session's landing, the person being at that keyboard; `settled` (a fresh idle write with no turn seen running) clears only the question. Questions expire after `WAIT_TTL_MS` (12h), and once the first scan resolves the desk re-reads each saved one's tail (`recheckAsks`, `readTurnState`) and keeps only those still asking. A spawned session's log is observed too: an observed ending is skipped while a flight holds the id (copilot: the provider+cwd), and inside `OBSERVED_ECHO_MS` of a spawned ending. (3) Red pull requests: the `github:prs` handler hands every list it returns to `prsUpdated` (the badges' own refresh — never a poller), and an open PR with failing checks or changes requested on a branch an indexed session is on (`prCarrier` in index.ts, newest session on `headRefName` under that repo root) is raised once per `headSha` (`seenPrs`, persisted with the entries; going green forgets it, so red again on the same commit is news), cleared when it goes green or leaves the list — an empty list is a failed `gh` call and clears nothing. Main owns the *unseen* set — keys are the session id, `table:<id>`, `turn:<id>` (copilot, until the index resolves it by cwd + start time), `asks:<id>` and `pr:<root>#<n>` — persisted to `userData/attention.json`, because only main sees every turn end; `landings()` folds it to one `Landing` per session with its most urgent kind (`asks` > `pr` > `landed`) and the Dock badge counts the same one per session, the renderer pushes what the window shows (`setAttentionFocus`), window focus comes from the `BrowserWindow`, and `landed.ts` in the renderer only mirrors the set (`onLandings`). Endings inside `BURST_MS` share one notification (mixed kinds are counted by kind); opening a session clears every reason it carried, its badge count and withdraws its banners. Switches live in config (`attention`, one set for every kind); an unflipped one is on only in a packaged app, so dev, e2e and the UI tour stay silent. macOS refuses notifications from unsigned builds (`UNErrorDomain error 1`) — the desk bounces the Dock icon instead. `-core.ts` is the IO-free half (what the unit tests target); `attention.ts` holds the desk and the one Electron surface (`electronSurface()`), which tests replace.
- `instructions-core.ts` vs `instructions.ts` — the shared-instructions marker/drift logic is deliberately IO-free in `-core.ts` (that's what the tests target); keep IO in `instructions.ts`. `instructions-share.ts` is how a repo's baseline reaches teammates: the repo itself is the medium, so the block is written into that repo's own `CLAUDE.md`/`AGENTS.md` in a fresh worktree off `origin/HEAD` (never the user's checkout) and opened as a PR — an already-open instructions PR gets the commit pushed onto its branch rather than a second PR, and "the repo already says this" is decided from `git show <base>:<file>` before any branch exists. Symlinked targets are resolved (this repo's own `CLAUDE.md` is a link), written once, and refused if they point outside the worktree. Coming back the other way, a repo scope with no stored baseline adopts whatever block its files already carry (`adoptableBlock`) and a drifted file's block can be taken as the baseline (`adoptInstructionsFrom`) — that is how a teammate's merged change arrives. Global scopes never adopt: a stale `~/.claude/CLAUDE.md` is nobody's share.
- `workspace.ts` — "always worktrees, always PRs": new sessions get a `cockpit/<name>` branch in an isolated worktree under the app's userData, never in the user's checkout; PRs go through `gh`.
- `diff.ts` + `diff-core.ts` — the review before landing: a worktree's changes against its base branch (or the index's two sides), read-only git, every read bounded. `pr-feedback.ts` + `pr-feedback-core.ts` — the loop after the PR opens: one open PR's checks (`gh pr checks --json`, gh's own `bucket` decides what failed), unresolved review threads, change requests and conflicts (`gh api graphql`, owner/repo left to gh's `{owner}`/`{repo}` placeholders), read on demand, never polled; the "Fix with <agent>" prompt quotes each failing Actions job's failed step (`gh run view --job --log-failed`, anchored on `##[error]`, excerpts cached per job id). The `-core.ts` halves are IO-free and are what the unit tests target; `src/shared/pr-feedback.ts` holds the verdicts both processes share.
- `cleanup.ts` + `cleanup-core.ts` — cross-agent, cross-repo disposal: what has gone stale past a configurable idle threshold (`staleDays`, default 30) and what can safely go. Worktrees are discovered by asking git itself per known repo root, so the ones Cockpit never cut (Claude Code's `.claude/worktrees`, hand-made) are found and cleanable too — `origin` marks which are ours. The unit is a piece of work, not a file: the worktree a stale session ran in rides on that session (`StaleSession.worktree`) and `deleteSessions` takes it with the log file, so every worktree appears exactly once across the report and the leftover list holds only the ones no session claims. The cascade is conservative — a worktree goes only when *every* session indexed in it is in the same deletion, and only when it is stale and unblocked. Archiving stays config-only and reversible. Deleting unlinks the provider's own log file (and, for Copilot, the session-state dir) after re-validating the path against both the index and the configured sources; worktree removal re-derives the git listing before acting and never passes `--force`; branches go only if `git branch -d` accepts them. Processes left behind are part of the same sweep: `lsof -d cwd` + `ps` find anything (a dev server, a watcher, a shell) whose cwd is inside a stale worktree, or inside a removed one — a directory at a worktree home's depth with no `.git`, even if a dev server recreated it (Cockpit's root and Codex's and Copilot's homes off their config homes at depth 2, a repo's `.claude/worktrees` at 1) — Cockpit's own process tree (what launched it and what it spawned) is never offered. A worktree with one inside is blocked (`process`) until it is stopped; stopping re-judges the pids and sends SIGTERM only, reporting survivors rather than escalating. `-core.ts` holds the IO-free half (porcelain, `lsof`/`ps` parsing, staleness, block rules, `judgeProcesses`) — that's what the unit tests target.
- `transcript-search.ts` — "where did I discuss X" across all three agents: full-text search over transcript *contents*, on demand. Candidate files come only from `SessionIndexer.transcriptCandidates` (the same visibility rules as `page()`, newest first) — the renderer never names a path. Each file is streamed in chunks under a per-file byte cap (`DEFAULT_MAX_BYTES_PER_FILE`, the head of a huge log), the loop yields to the event loop between files, a newer query or `cancel()` stops the one in flight, hits are capped per session and in total, and a wall-clock budget guarantees a return — the result says why it stopped (`stoppedBy`) and how many files were only partly read. User and assistant text only unless `includeTools`; Codex's item+echo duplicates collapse to one hit. No persisted index yet: at ~2,500 transcripts a scoped search returns in well under the budget, a global one may hit it — that is the follow-up if it does.
- `extensions.ts` — MCP/skills/plugins inventory and cross-agent sharing; each agent has its own config format (`~/.claude.json`, `~/.codex/config.toml`, `~/.copilot/mcp-config.json`).
- `accounts.ts` — who each agent CLI is signed in as, per config home (Claude `.claude.json` OAuth, Codex `auth.json` JWT, Copilot's multi-account `config.json`), plus the `gh` user for repo operations.
- `usage.ts` — subscription usage per provider without touching credentials: Claude measured locally from session JSONLs, Codex from the rate-limit snapshots its CLI persists, Copilot via the GitHub billing API (fails soft).
- `provider-archived.ts` — reads each provider's own archived/deleted state (Copilot `data.db`, Codex `archived_sessions/`, the Claude desktop app's session store) so those sessions never appear in Cockpit.
- `updates.ts` + `update-install.ts` + `update-install-core.ts` — `UpdateManager`: app updates from GitHub Releases. Only an installed macOS build is live (dev runs and Linux report `unsupported` and never touch the network). `electron-updater` is used for the **check alone** — `app-update.yml` → `latest-mac.yml` → version compare, on launch and every four hours — because its macOS installer is Squirrel.Mac, which only swaps in a bundle whose Developer ID signature matches the running one, and releases are ad-hoc signed (`cockpit-apple-signing`): every install used to end in `error`. Fetching and installing are Cockpit's own, which is also the only place that can clear the quarantine flag *before* the new bundle lands. Left alone it keeps itself current: `update-available` → download (`updates.download` config switch) → swap in on `before-quit` (`updates.install`), never under a running session; "Restart now" is the same swap, sooner. What Squirrel's signature check stood for is explicit in `stageUpdate`: the zip must hash to the feed's `sha512`, and the bundle inside must share the running one's `CFBundleIdentifier`, be the offered version, and match its team once one exists (`swapRefusal`). The swap is a detached `/bin/sh` script (`swapScript`) that waits for the app's pid, renames the old bundle aside in the same folder, `ditto`s the new one in and restores on failure — so a failed update always leaves a working app. It leaves one line in `<userData>/updates/last-install`, and a failure there holds the automatic path (`UpdateState.installFailure`) until the user checks by hand, so an uninstallable build is never re-fetched in silence; the staged build survives a quit (`resumeStaged`) so saying yes again costs no second download. State is pushed as `update-state`; Settings › About renders it. `-core.ts` is the IO-free half (asset choice, URL, refusals, the script's text) and is what the unit tests target; `tests/update-install.test.ts` builds real bundles in a tmpdir and runs the script for real.
- `github.ts` + `github-core.ts` — PR badges: one `gh pr list --json` per repo root, plus — only when a PR is open — one `gh api graphql` over the open PRs' review threads (`gh pr list` has no such field; `{owner}`/`{repo}` left to gh's placeholders), both in the same 60s cache entry. The list fails soft to an empty list, the thread call to counts of 0. `-core.ts` is the IO-free half (what the unit tests target): it folds each PR's `statusCheckRollup` into `PrStatus.checks` (`passing | failing | pending | none` — any failure wins, then any unfinished or unrecognized run, else passing), `reviewDecision` into `PrStatus.review`, and the explicitly unresolved threads into `PrStatus.unresolvedThreads` (open PRs only), reusing `pr-feedback-core`'s GraphQL node helpers.
- `backup.ts` + `backup-core.ts` — one file holding everything of Cockpit's own that is worth keeping: sources, instruction baselines, library entries and the skills behind them, provider definitions and the session maps. Never session logs, worktrees or the index (rebuildable or machine-local). Repo scopes travel as the indexer's own `gh:owner/repo` key with the original root alongside, so a same-machine restore lands on the exact checkout and another Mac still matches by repo. Secrets — provider keys, MCP `env`/`args`/`url` — only enter the file behind a passphrase (scrypt + AES-256-GCM, fixed parameters, AAD-bound to the header); without one they are left out and the entry records `withheld`, which makes a switch refuse rather than write blank credentials. Restore is a merge that only ever *adds* (local state is what the agents actually run), so re-running the same file is a no-op and picks up repos cloned since; restored entries land as `pending` rows for the user to switch on, never written into agent configs by the restore itself. A raw snapshot of the config goes to `<userData>/backups/` first and backs the undo. `-core.ts` holds the IO-free half — `sanitizeBundle` (the file is untrusted input), the sealing, and `planRestore` — which is what the tests target; `index.ts` injects the dialogs, the keychain and the indexer's repo map, so the whole round trip runs headless.
- `env.ts` — `cliEnv()`: GUI apps on macOS get a minimal PATH; use it for every spawned CLI. `execText(cmd, args, opts)` is the one way to run a CLI and read its output — it never rejects, so each caller decides what failure means (throw, fall back, log); don't hand-roll another `execFile` wrapper.

### `src/shared/` — what both processes agree on

Pure and IO-free by construction: every module imports nothing but its own siblings (no `node:*`, no `electron`, no reach into `src/main` or `src/renderer`), which is what lets the sandboxed renderer load the same file main does. `tests/shared-purity.test.ts` pins that, and the layering above. Check this list before writing a helper — several of these exist because the same rule was about to be implemented twice, once per process, and drift.

- `types.ts` — the domain vocabulary, a leaf. `contract.ts` — `CockpitApi` plus the `CH`/`PUSH` channel names (above).
- `asks.ts` — the question an agent stopped to ask, and what a pick turns into: the provider tool calls that are really questions (Claude's `AskUserQuestion` / `ExitPlanMode`, Codex's `request_user_input`). Copilot's permission prompts are deliberately out — answering one needs the blocked process.
- `endpoints.ts` — custom model providers (BYOK): validation, env translation, the `/models` request/response shapes.
- `acp.ts` — the Agent Client Protocol wire types and the agent-definition rules the sanitizer enforces.
- `library.ts` — reconciling Cockpit's own config (what you asked for) against each agent's real config (what it has).
- `instruction-markers.ts` — the managed-block markers, defined once so the writer and the review can never disagree. `instruction-changes.ts` — what applying a baseline would do to one agent file, the pre-apply review. `line-diff.ts` — the LCS line diff both of those draw with (pure, no DOM).
- `repo-order.ts` — the order projects are listed in (A→Z, or the user's drag order; never session activity, which would move rows under the cursor).
- `roundtable.ts` — seat identity: the names agents call each other in prompts and the UI shows on seats.
- `pr-feedback.ts` — the verdicts both processes read off a PR's checks and threads.

### Tests

Three tiers; CI (`.github/workflows/ci.yml`) runs all of them:

- **unit** (`tests/*.test.ts`, node env) — real tmpdir fixtures: tests write fake session logs and fake `.git/config` files to disk and run the real indexer/parsers over them. No mocking framework; follow that pattern for new tests.
- **component** (`tests/component/`, jsdom) — renderer components against the stubbed `window.cockpit` in `tests/component/stub-api.ts`.
- **e2e** (`tests/e2e/`, Playwright) — drives the built Electron app; requires `npm run build` first. `a11y.spec.ts` walks every view against the ui-tour's fixture world and asserts the accessibility rules a machine can settle — what a `role=tree` may own, a name on an element whose role cannot expose one, a level-one heading and landmarks, a control with neither text nor a name, a scrollable region no keyboard can reach, and an ARIA relationship pointing at an id that isn't there. Each check is a rule this app has already broken, written out in the file rather than pulled from an audit engine: no dependency, and no failure whose reason isn't visible in the spec. Contrast and focus order are deliberately out of scope — they stay with the design-system review. `packaged.spec.ts` is the exception: opt-in via `npm run test:packaged`, it launches the `.app` from `npm run package` and is skipped otherwise. Every spec tears its app down with `closeApp` (`tests/e2e/close-app.ts`), never a bare `app.close()` or a SIGKILL of `app.process()`: Playwright's close waits until every stdio pipe shuts, and Chromium's helper processes hold those pipes past the main process, so only a process-group kill bounds teardown.

Not a tier, but the check for anything a person *sees*: `npm run ui:tour` (above). Tests assert behaviour; the tour shows what renders. Its world (`scripts/ui-tour/world.mts`) is fake `HOME` + `COCKPIT_USER_DATA` + stub `claude`/`codex`/`copilot`/`gh` first on `PATH` — main resolves every agent path through `os.homedir()`, so that is all hermeticity takes. `tests/ui-tour-world.test.ts` parses the world with the real parsers, so log-format drift fails a test instead of quietly emptying the screenshots.

## Packaging & releases

- `electron-builder.config.js` packages macOS only: dmg + zip per arch (arm64, x64), asar with `out/**` and `package.json` and nothing from `node_modules` (main and preload are single bundled files), fuses flipped (`runAsNode` off, `NODE_OPTIONS` off, asar integrity on; `--inspect` stays on because Playwright attaches to the packaged bundle through it in the smoke test). Production `dependencies` ship in the asar — electron-vite leaves them external for main (`require('electron-updater')` at load) — so a dependency dropped from the asar throws at startup as a modal with no window. Signing/notarization turn on by the presence of the five Apple secrets (`CSC_LINK`, `CSC_KEY_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`), all or none — a partial set throws at config load. With them signing is mandatory (`forceCodeSigning`) and `scripts/verify-signing.mts`, which ends `npm run package`, asserts a Developer ID signature for that team, the hardened runtime, a stapled notarization ticket and Gatekeeper acceptance on every bundle; without them the build is ad-hoc, the same script asserts it stayed so, and nothing fails — never make a credential-less build fail.
- Third-party notices are generated, never hand-written: a plugin in all three electron-vite targets (`scripts/licenses/`) writes `out/THIRD_PARTY_NOTICES.txt` from what the bundles inline plus the production dependency tree, and `extraResources` ships it with Electron's `LICENSES.chromium.html` to `Contents/Resources`, where Settings › About opens it. A copyleft or unstated license only warns (`refusal` in `notices-core.ts`) — the build also runs on dependency-update PRs; artwork or fonts copied into the source need an entry in `fixedNotices`.
- The app icon ships as a committed `build/icon.icns`, packed by `npm run icon` (`scripts/build-app-icon.swift`, macOS only) from `resources/icon-original.webp`; the same run writes `resources/icon.png`, the dev Dock icon. Never let electron-builder render the `.icns` from a PNG: its converter puts the 16/32/64px sizes in chunk types Finder decodes as noise (`tests/app-icon.test.ts` guards the layout). Rerun after changing the artwork and commit both outputs.
- `package.json` `version` is `0.0.0` on purpose: semantic-release (`.releaserc.json`) derives the version from the commits since the last tag and stamps it at release time; the tag is the version and nothing is committed back. Commit types decide the bump (`feat` minor; `fix`/`perf`/`revert`/`build` patch; `!` major) — a misnamed commit is a wrong version.
- CI builds the app the same way on pull requests and `main`: `ci` → `package` (read-only token, macOS) → `release` (write token, `main` only). `package` decides the version first with `scripts/next-version.mts` (semantic-release's own commit analyzer over the `.releaserc.json` rules; the decision is `-core.mts`, what the tests target), stamps it when a release is due (otherwise the build is `0.0.0`), then runs `npm run package` → `test:packaged` against that version and uploads the files to the run. Only on `main` does it enter the `release` environment, the one place the Apple secrets live. `release` runs only when a version is due: it downloads those files, and semantic-release tags and creates the GitHub Release with the assets and `latest-mac.yml` without building anything, refusing to publish if its version differs from the one packaged (`verifyReleaseCmd`), then attests provenance.

## UI work

Before touching anything in `src/renderer/`, read `design-system/cockpit/MASTER.md`. Per-view rules in `design-system/cockpit/pages/<view>.md` override it. Canonical design tokens live in the `:root` block of `src/renderer/src/style.css` — components use tokens only, never raw hex. Dark mode only.

## Documentation

The user guide is a VitePress site in `docs/` (`docs/guide/`, one page per feature). It is
**deliberately not deployed** — there is no Pages workflow and none is wanted yet. It is read
locally with `npm run docs:dev`, so treat it as part of the repo rather than as a published site.

Keep it current in the same commit as the change: anything that alters what a user sees or does —
a new view, a renamed control, a changed default, a new setting — updates its page under
`docs/guide/`. Nothing in CI checks this, so the rule is the only thing that catches drift.

## Repo skills

Project skills (Agent Skills standard, `SKILL.md` format) live in **`.agents/skills/`** — the single source of truth. Codex and Copilot read that directory natively; `.claude/skills` is a symlink to it for Claude Code. Add new skills there, one directory per skill:

- `add-ipc-capability` — the recipe for extending the renderer↔main IPC surface

- `cockpit-ui` — design-system compliance for renderer work

## Conventions

- Conventional Commits (`feat(indexer): …`, `docs: …`), matching existing history.
- No AI attribution: no `Co-Authored-By` lines or "Generated with" footers in commits or PRs.

### File naming

- Non-component modules and tests: lowercase, kebab-case when multiword (`dev-window.ts`, `instructions-core.ts`, `stub-api.ts`).
- React components: PascalCase `.tsx`, named for the component (`ChatView.tsx`). A `.tsx` file that is not itself a single component stays lowercase (`logos.tsx`, `main.tsx`).
- Tests are named after the module under test, kebab-cased (`home-view.test.tsx` for `HomeView.tsx`); `.test.ts(x)` for vitest tiers, `.spec.ts` for Playwright e2e.
- Entry points are `index.ts` / `main.tsx`; directories are single lowercase words.
- CSS class names are kebab-case; symbols follow standard TS style (camelCase values, PascalCase types/components, SCREAMING_SNAKE module-level constants).

### Code style

- **`type`, not `interface`.** Declare object shapes as type aliases; compose with intersections
  (`type B = A & {…}`) instead of `extends`. The one exception is declaration merging that
  TypeScript only allows through interfaces (e.g. the `declare global { interface Window }`
  augmentation in `src/renderer/src/api.ts`).
- **`readonly` properties by default.** Every property of a shared or exported type is `readonly`
  unless in-place mutation is the point (e.g. a main-process cache/accumulator) — leave a comment
  on the property when you opt out. To derive a mutable working shape from a readonly type, map it
  (`{ -readonly [K in keyof T]: T[K] }`) rather than duplicating the shape.
- **Max 3 function parameters.** A signature that wants a 4th parameter gets restructured instead:
  keep the 1–2 primary arguments positional and gather the rest into a single (usually optional)
  options object. Never grow trailing boolean/optional parameter lists.
